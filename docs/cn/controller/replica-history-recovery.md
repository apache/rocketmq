# 恢复因日志历史不一致而隔离的副本

Windows 上的 Store 应使用 NTFS，broker 运行账户需要具备打开相关目录进行写入并刷新目录的权限。若刷新失败，broker 会拒绝继续握手或恢复。英文操作说明末尾提供 Windows PowerShell 授权与撤回命令。

健康副本收到完整握手后会将候选截断位点和本地确认位点写入 `ha-history-received`，再执行对应决定。重启时重新执行完整记录中的比较结果。如果日志不完整或无法读取，副本保持隔离。备份时应保留此文件。

Controller 模式下，如果握手要求截断到本地确认位点之前，副本会拒绝复制，并在自己的 `storePathRootDir` 下写入 `ha-history-incident`。此后即使主节点在同一个 epoch 继续写入，副本也保留已记录的最小截断位点。带有该记录的副本不能完成主节点提升。允许非正常选主不会自动授权丢弃本地消息。

1. 找到**被隔离的副本**，通常是原主节点。保持当选主节点作为复制源。停止被隔离副本，备份其完整 Store、独立配置的 CommitLog 和 epoch 路径，并保留该副本自己的 broker 身份。
2. 在停止的副本上查看 `ha-history-incident`。六行内容依次为本次事件 ID、截断位点、检测时的确认位点、原本地日志末端、预期主节点 HA 地址及有序的 `epoch@起点` 列表、SHA-256 校验和。独立确认当选主节点的身份，并用可信源的实际 CommitLog 字节核对要保留的前缀。相同的 epoch 和位点无法证明消息内容一致。无法核实前缀或已无法读取截断位点时，应从当选历史的可信快照重建副本。
3. 授权将丢弃从截断位点到本地末端的全部消息，包括已经确认的消息。例如截断位点为 1580、原确认位点为 3280 时，即使主节点已经写到 4190，副本仍会丢弃 `[1580, 3280)`。确认接受数据损失后，在停止的副本的 Store 根目录运行[英文操作说明](../../en/controller/replica-history-recovery.md)中的授权命令，将已核对的记录原子复制为 `ha-history-approval`，并同步文件与目录。
4. 将该副本作为当选主节点的从节点重启。握手匹配后，副本先使本次授权失效，再执行截断。检查复制追平情况，并核对新消息内容。若要撤回尚未使用的授权，请停止副本，在 Store 根目录执行英文说明中的撤回命令，删除授权文件并同步目录。保留 `ha-history-incident`，直至恢复过程自行清除它。已执行的截断只能通过备份恢复。

目标地址、epoch 历史或截断位点变化时，需要重新核对新事件。健康副本在等待首个握手响应时重启，可以正常重新连接。已隔离的副本再次请求历史前会写入 `ha-history-inspecting`。若此时崩溃或存储失效，副本可能已观察到更小的截断位点，下一次可用握手会使旧授权失效并提出从零截断。请保留两个事件文件。如果恢复中断，检查磁盘状态和新记录后再决定是否重新授权。记录损坏、持久化失败或找不到共同 epoch 时，副本继续保持隔离。
